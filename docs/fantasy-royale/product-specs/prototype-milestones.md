# Prototype Milestones

## 方針

プロトタイプ完成までのマイルストーンを大きめに分ける。
詳細なクラス構成や仕様は、各マイルストーン開始前に相談して決める。

現状はMilestone 1の96x72森林Reference Map、移動・地形判定・Camera追従、自由配置EventSocket、回復の泉を通す共通Event Runtime、6候補から3地点を選ぶ再現可能なEvent Pool抽選まで一時`PreviewDebug`足場で検証済み。Milestone 2はStep 1で純C# Character Health、Step 2で共通Move Command、本番`CharacterActor2D`、人間入力Adapterを実装し、Previewを本番移動経路へ移行した。攻撃、装備、正式Character Prefabは未着手。

## マイルストーン案

### Milestone 1: ビジュアル・探索マップ基盤

目的:
- コンセプトアート準拠の見た目で、探索できる固定マップを作る。
- 複数ロケーション、タイル、オブジェクト、当たり判定、カメラ、ランダム配置ポイントを確認する。

主な成果物:
- 草原、森、水辺、雪原、火山などの固定マップ。
- タイル素材とオブジェクト素材。
- 建物、商人候補、草むら、木、岩、池、橋、道、崖など。
- 地形当たり判定。
- ランダム配置ポイントの初期設計。

### Milestone 2: アクション戦闘基盤

目的:
- ゼルダ風のトップダウン戦闘を成立させる。
- 装備によって通常攻撃や特殊アクションが変わる土台を作る。

主な成果物:
- 移動。
- 通常攻撃。
- 魔法または特殊アクション。
- 武器ごとの攻撃範囲。
- 被弾、HP、撃破。
- 攻撃エフェクト。
- 装備によるアクション差し替え。

### Milestone 3: 試合ループ基盤

目的:
- 一試合の開始から終了までの最小ループを作る。

主な成果物:
- 試合開始。
- プレイヤー/CPUスポーン。
- ランダム配置。
- 脱落。
- 観戦。
- 勝敗判定。
- 約20分を有力案とする試合進行。移動速度、エリア収縮、遭遇密度を接続するまで未確定。

### Milestone 4: 簡易CPU対戦

目的:
- 一人用で対戦テストを回せるようにする。

主な成果物:
- 簡易CPU。
- 探索。
- 近接戦闘。
- 逃走。
- アイテム/商人利用の最小判断。

### Milestone 5: エリア収縮・バトロワ成立

目的:
- バトロワとして終盤にプレイヤーが集まる流れを確認する。

主な成果物:
- エリア収縮。
- エリア外継続ダメージ。
- 収縮速度調整。
- 最終盤の遭遇確認。

### Milestone 6: アイテム・商人・装備拡張

目的:
- 試合中に強化され、アクションが変化する体験を確認する。

主な成果物:
- システム確認用の数個のアイテム。
- 武器装備。
- 魔法/特殊アクション装備。
- 商人購入。
- 装備による攻撃範囲や挙動の変化。

### Milestone 7: マルチプレイ準備

目的:
- 最終的にオンラインマルチ必須である前提から、同期に必要な構造を検証する。

主な成果物:
- 入力コマンドの整理。
- 試合状態の同期候補整理。
- CPU/人間/ネットワーク入力の共通化方針。
- 実装開始するか、設計だけ固めるかの判断。

### Milestone 8: プレイテスト調整

目的:
- 約20分の試合として成立するように調整する。実測により再検討する。

主な成果物:
- マップ密度調整。
- 収縮速度調整。
- CPU強さ調整。
- アイテム出現率調整。
- 戦闘テンポ調整。

## 次に相談する対象

次はMilestone 2 Step 3として、最初の通常攻撃と装備アクション基盤を相談する。

- 攻撃方向を4方向、8方向、自由照準のどれにするか。
- Attack Commandへ方向、対象、押下 / 保持など何を含めるか。
- Coreの攻撃範囲・Damage結果と、Unity PhysicsのOverlap / Colliderによる命中候補取得をどう分けるか。
- 発生、持続、硬直、移動可否、割込みをどこまで最初の時間モデルへ含めるか。
- 装備DefinitionをScriptableObjectにする場合の通常攻撃 / 特殊アクションSlotと、Runtime装備状態の最小構造。
- 最初の検証武器を近接一種にするか、近接と遠隔を同時に通して差し替えを実証するか。

正式Character素材、Animation構成、CPU / Network入力Adapter、観戦、復活専用処理はStep 3へ自動的に含めない。
